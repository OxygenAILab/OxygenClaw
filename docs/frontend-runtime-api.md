# OxygenClaw Frontend Runtime API Contract

This document is the stable backend contract for the upcoming WebUI rewrite.

## Base URL

- Development API base: `http://localhost:3001/api`
- Frontend dev server usually proxies or calls `/api`.
- Auth token, when available: `Authorization: Bearer <token>`.

## Response Envelope

Most JSON endpoints return:

```json
{
  "success": true,
  "data": {}
}
```

Errors return:

```json
{
  "success": false,
  "error": "message"
}
```

## Version And Health

### `GET /api/health`

Returns:

```json
{
  "success": true,
  "data": {

    "timestamp": "2026-07-04T00:00:00.000Z",
    "version": "26.0.0-alpha.1",
    "displayVersion": "v26.0 Alpha 1"
  }
}
```

## Conversations

Conversations are the persistent chat/task UI timeline.

### `GET /api/conversations?mode=chat`

Returns recent conversations.

### `POST /api/conversations`

Request:

```json
{
  "title": "New conversation",
  "modelId": "providerId:modelName",
  "mode": "chat",
  "capability": "fast"
}
```

### `GET /api/conversations/:id`

Returns:

```json
{
  "success": true,
  "data": {
    "conversation": {
      "id": "uuid",
      "title": "title",
      "mode": "chat",
      "capability": "fast",
      "modelId": "providerId:modelName",
      "createdAt": 1783140000000,
      "updatedAt": 1783140000000
    },
    "messages": [
      {
        "id": "uuid",
        "conversationId": "uuid",
        "role": "user",
        "content": "hello",
        "attachments": null,
        "timestamp": 1783140000000
      }
    ]
  }
}
```

### `POST /api/conversations/:id/messages`

Generates a chat response and persists user/assistant messages.

Request:

```json
{
  "content": "hello",
  "modelId": "providerId:modelName"
}
```

SSE response uses OpenAI-compatible chunks:

```text
data: {"choices":[{"delta":{"content":"Hello"}}]}

data: [DONE]
```

### Save Message Without Generation

`POST /api/conversations/:id/messages`

Request:

```json
{
  "role": "assistant",
  "content": "result text",
  "generate": false
}
```

Use this for task/computeruse outputs that are generated by runtime APIs.

## Runtime Tasks

Runtime tasks are persistent execution records. New WebUI should treat these as the source of truth for task/computeruse execution state.

### Runtime Task Object

```json
{
  "id": "uuid",
  "userId": null,
  "conversationId": null,
  "kind": "agent",
  "prompt": "task prompt",
  "task": "task prompt",
  "mode": "task",
  "capability": "fast",
  "modelId": "providerId:modelName",
  "status": "running",
  "result": "optional result",
  "error": "optional error",
  "createdAt": 1783140000000,
  "startedAt": 1783140000000,
  "updatedAt": 1783140000000,
  "completedAt": null,
  "cancelledAt": null,
  "metadata": {},
  "events": [],
  "workerRuns": [],
  "steps": []
}
```

Statuses:

- `pending`
- `running`
- `completed`
- `failed`
- `cancelled`

`pending` means the task has been accepted by the runtime queue but has not started executing because the worker manager is applying concurrency limits.

Kinds:

- `agent`
- `computeruse`

## Agent Execution

### `POST /api/agent/execute`

Starts a runtime task and streams live events in the same request. Also persists into `runtime_tasks`, `runtime_events`, and `worker_runs`.

Request:

```json
{
  "prompt": "do something",
  "mode": "task",
  "capability": "fast",
  "modelId": "providerId:modelName"
}
```

### `POST /api/agent/start`

Starts a runtime task and returns JSON immediately. Prefer this for long-running tasks.

Request body is the same as `/api/agent/execute`.

```json
{
  "success": true,
  "data": {
    "taskId": "uuid",
    "workerRunId": "uuid",
    "status": "pending",
    "eventsUrl": "/api/agent/tasks/uuid/events/live"
  }
}
```

SSE event examples:

```text
data: {"type":"task_start","taskId":"uuid","status":"running"}

data: {"type":"step","step":{"type":"think","content":"...","timestamp":1783140000000}}

data: {"type":"task_complete","taskId":"uuid","status":"completed","result":"...","steps":[]}
```

Failure still returns a completed SSE stream with persisted events:

```text
data: {"type":"task_complete","taskId":"uuid","status":"failed","error":"TypeError: fetch failed","steps":[]}
```

## ComputerUse Execution

### `POST /api/agent/computeruse/execute`

Request:

```json
{
  "task": "open app and inspect screen",
  "modelId": "providerId:modelName"
}
```

SSE event format is the same as agent execution. `step.action` may exist for GUI actions.

### `POST /api/agent/computeruse/start`

Starts a ComputerUse runtime task and returns JSON immediately. Request body is the same as `/api/agent/computeruse/execute`.

## Runtime Query APIs

### `GET /api/agent/tasks`

Returns recent runtime tasks.

### `GET /api/agent/tasks/:id`

Returns one task with `events`, `workerRuns`, and derived `steps`.

### `GET /api/agent/tasks/:id/events`

Returns persisted event history.

Optional query:

- `afterSeq`: only return events with `seq > afterSeq`

Example:

```http
GET /api/agent/tasks/:id/events?afterSeq=3
```

### `GET /api/agent/tasks/:id/events/stream`

Replays persisted events as SSE and ends with `[DONE]`.

Optional query:

- `afterSeq`

SSE replay event:

```text
data: {"type":"step","seq":4,"step":{"type":"output","content":"..."}}

data: [DONE]
```

### `GET /api/agent/tasks/:id/events/live`

Replays persisted events after `afterSeq`, then stays connected and streams new events until a terminal event arrives.

Optional query:

- `afterSeq`

Use this with `/api/agent/start` or `/api/agent/computeruse/start`.

### `GET /api/agent/tasks/:id/workers`

Returns worker lifecycle records.

```json
{
  "success": true,
  "data": {
    "taskId": "uuid",
    "workerRuns": [
      {
        "id": "uuid",
        "taskId": "uuid",
        "workerType": "local-agent",
        "status": "failed",
        "startedAt": 1783140000000,
        "heartbeatAt": 1783140000000,
        "completedAt": 1783140000000,
        "exitReason": "TypeError: fetch failed",
        "metadata": {}
      }
    ]
  }
}
```

### `GET /api/agent/runtime/workers`

Returns the in-process worker manager state.

```json
{
  "success": true,
  "data": {
    "maxConcurrency": 2,
    "queued": 0,
    "running": 1,
    "adapters": ["local-agent", "local-computeruse"],
    "tasks": {
      "queued": [],
      "running": [
        {
          "taskId": "uuid",
          "workerType": "local-agent",
          "startedAt": 1783140000000,
          "heartbeatAt": 1783140000000,
          "cancelled": false
        }
      ]
    }
  }
}
```

### `GET /api/agent/runtime/workers/capabilities`

Returns registered worker adapters and their availability.

```json
{
  "success": true,
  "data": {
    "workers": [
      {
        "type": "local-agent",
        "label": "local-agent",
        "available": true,
        "default": true,
        "isolation": "process",
        "supportsCancel": true,
        "supportsHeartbeat": true,
        "supportsArtifacts": false
      },
      {
        "type": "container-agent",
        "label": "Container Agent",
        "available": false,
        "default": false,
        "isolation": "container",
        "supportsCancel": true,
        "supportsHeartbeat": true,
        "supportsArtifacts": false,
        "reason": "Disabled by default; set RUNTIME_ENABLE_CONTAINER_AGENT=true after sandbox image wiring is complete."
      }
    ]
  }
}
```

`POST /api/agent/start` and `POST /api/agent/execute` accept optional `workerType`. Supported values are currently `local-agent` and `container-agent`. New frontends should default to `local-agent` unless capabilities report that another worker is available.

Compatibility additions for the current WebUI:

- `POST /api/agent/execute` returns the same JSON shape as `/api/agent/start` when the request does not explicitly accept `text/event-stream` and does not set `stream: true`.
- `GET /api/agent/tasks/recent?limit=10` returns `{ tasks, total }`.
- `GET /api/agent/history?limit=50` returns `{ tasks, total }`.

## Frontend Compatibility Notes

- `GET /api/auth/me` now returns the user object directly in `data` for the current WebUI contract.
- `POST /api/llm/image/generations` proxies OpenAI-compatible image generation providers and returns `{ created, data }`.
- `PUT /api/settings` accepts the current WebUI image generation and dashboard API settings fields.
- `GET /api/settings` normalizes boolean settings to booleans instead of raw `0/1` values.
- `POST /api/cli/exec` returns `command`, `stdout`, `stderr`, `output`, and `exitCode`.

### `POST /api/agent/tasks/:id/cancel`

Cancels or marks a running task as cancelled.

### `DELETE /api/agent/tasks/:id`

Deletes runtime task, runtime events, worker runs, and legacy `agent_tasks` compatibility row.

## Recommended Frontend Flow

### Chat

1. Create or load conversation.
2. Use `/api/conversations/:id/messages` SSE for chat.
3. After `[DONE]`, reload `/api/conversations/:id` to sync message IDs.

### Task

1. Create or load conversation.
2. Save user message with `generate:false`.
3. Prefer `POST /api/agent/start` for long-running tasks.
4. Subscribe to `/api/agent/tasks/:taskId/events/live?afterSeq=<lastSeq>`.
5. Render live SSE events.
6. On reconnect, call `/api/agent/tasks/:taskId/events?afterSeq=<lastSeq>` or `/events/live`.
7. Save final assistant message to the conversation with `generate:false`.

### ComputerUse

Same as task, but call `/api/agent/computeruse/execute` and render `step.action` when present.

## Important Current Limits

- Runtime tasks are persistent and local workers now run behind an in-process worker manager with queueing, concurrency limits, heartbeat, and stale-task sweep.
- Workers are still in-process, not separate OS processes or containers yet.
- `container-agent` is registered as a non-default scaffold. It reports Docker/runtime availability but intentionally fails safely until sandbox image wiring is implemented.
- On server restart, orphan `pending`/`running` tasks are marked failed with `Runtime worker interrupted by server restart`.
- Container workers are not implemented yet.
- True PTY terminal sessions are not implemented yet.
- ComputerUse operator abstraction still needs the next backend phase.
- Attachments are not fully persisted as first-class artifact records yet.
